1. What runs
------------
- Driver: tools/requant_full.py @ 371f9a1. Workers run the frozen copy in OUT/code (OUT/code/COMMIT),
  so later edits in the worktree do not change the running job. OUT/code is synced to spark2.
- Image: dsv41-quant151 (sha256:ba0ac163ef95dcdce2b403293956f6dc08e2df8d80a4dbadae39d37736c27d6f),
  exllamav3 1.5.1 @958ec93. Loaded on both nodes, same ID (docker save | ssh spark2 docker load, 2m38s).
- Encoder: exllamav3 1.5.1 quantize_tiles (tail-biting Viterbi, not greedy) through the recipe's
  _quantize_fast (meta-H q_fallback, skip_g_scale), 2.0 bpw, MCG codebook (p2b cb=1), K=2, tile_chunk 4608
  (bitwise equal to 256). Then refit_scales with H = I (closed form, requant_probe.refit_identity), kept
  per tensor only when relerr does not rise. Per-tensor RNG seed = crc32(tensor name), so a unit's output
  does not depend on which node encodes it or in what order.
- Source (read-only): ~/.cache/huggingface/hub/models--deepseek-ai--DeepSeek-V4.1-Flash/snapshots/
  dba1be0a40aa45a94ad051997016db3960a90277. That is the snapshot the original pack was built from. spark1 has all
  shards. spark2 has source shards 23-42 only.
- Reference (read-only): snapshots/2.0bpw-mcg of models--sfxnz--DeepSeek-V4.1-Flash-EXL3. It is used for the
  layout check and the stock relerr column. 2.0bpw-mcg-lmhead-mxfp8 symlinks its shards 3-42 here.
- Units: 40 output shards, model-00003 through model-00042. Each has 1152 routed-expert tensors (w1/w2/w3 of
  384 experts), 46,080 tensors in total.
- Gate per unit, fixed before the run. A unit that fails any check is never written to shards/. The worker
  retries it once, then stops.
    * every relerr is finite, and the unit mean relerr is <= 0.97 x the stock 2.0bpw-mcg mean on the same tensors
    * the safetensors layout matches the same 2.0bpw-mcg shard: keys, dtypes, shapes, data offsets and file size
    * non-expert tensors and .mcg markers are byte-equal to the reference shard
    * every written trellis/suh/svh reloads equal to the encoded tensor
- Outputs, kept on the node that encoded them:
    OUT/shards/model-000NN-of-00048.safetensors   (3,585,xxx,xxx bytes each, mode 0644, owner sfxnz)
    OUT/units/NN.json      unit record + 1152 per-tensor rows (viterbi / final / stock relerr, refit kept,
                           t_enc / t_all seconds)
    OUT/logs/run-<node>.log  worker log: claims, 32-tensor progress lines, DONE per unit
- State, on spark1 only (OUT/state):
    units.json                    unit -> shard file
    claims/NN/                    claim, made by atomic mkdir (spark2 does it through ssh spark1)
    claims/NN/owner.json          node that claimed the unit
    claims/NN/heartbeat.json      progress, rewritten every 32 tensors
    done/NN.json                  verified unit: node, sha256, size, relerr stats, timings, code commit
    manifest.json                 aggregate of done/, refreshed after every unit
    DONE                          global marker, written when all 40 units have done records

7. Stop, resume, failures
-------------------------
- Graceful stop after the current unit: touch OUT/STOP (all nodes), or OUT/STOP.spark1 / OUT/STOP.spark2 (one
  node). Remove the file before resuming.
- Hard stop: docker stop dsv41-requant. The node keeps its claim. On resume, that node re-encodes the
  unfinished unit. A shard that was fully written and verified is reused after a sha256 re-check.
- Resume, on the same node: docker rm dsv41-requant, then run the same launch command (section 3 or 4).
  It is idempotent. Units that have done records are skipped, and this node's unfinished claim is resumed.
- If a unit fails twice (gate, verify or CUDA error), the worker exits with rc 2 and keeps the claim.
  Look at OUT/logs/run-<node>.log and OUT/units/NN.failed.json. Never loosen the gate to get past a failure.
- A claim can go STALE on a node that will not come back. First make sure no worker runs on that node
  (docker ps there). Then rm -r OUT/state/claims/NN on spark1. The next worker to pass that unit claims it.
  If no worker is left running, relaunch one.
- After a reboot nothing restarts on its own (--restart no). Resume as above.

9. Assembly (after DONE; run on BOTH nodes)
-------------------------------------------
  on spark1:  python3 /home/sfxnz/projects/data/dsv41-requant-viterbi/code/tools/requant_full.py assemble --node spark1
  on spark2:  ssh spark2 python3 /home/sfxnz/projects/data/dsv41-requant-viterbi/code/tools/requant_full.py assemble --node spark2 --state-host spark1

  What assemble does (host python, stdlib only, idempotent):
  a. Refuses unless state/DONE exists. Rebuilds the manifest from state/done/ and refuses unless all 40 units have
     records. It does not read manifest.json for this, because a stale manifest could let an old shard through.
  b. For every unit made on the other node: rsync -a --partial <node>:OUT/shards/<file> into OUT/shards/. Then every
     one of the 40 files must match the manifest's size and sha256.
  c. Builds ~/.cache/huggingface/hub/models--sfxnz--DeepSeek-V4.1-Flash-EXL3/snapshots/2.0bpw-mcg-viterbi-lmhead-mxfp8/
     by mirroring snapshots/2.0bpw-mcg-lmhead-mxfp8:
       - model-00003..00042: hard links to OUT/shards (same filesystem; a symlink out of the HF cache would
         dangle inside the serve container, which mounts only the cache)
       - model-00043 (the lm_head MXFP8 re-encode): symlink ../2.0bpw-mcg-lmhead-mxfp8/model-00043-of-00048.safetensors
       - model-00001/00002/00044..00048 and config.json, tokenizer*, LICENSE, etc.: the base's relative links
         (../2.0bpw-mcg/...). Non-expert tensors are unchanged and byte-equal (verified per unit).
       - model.safetensors.index.json: copied from the lmhead base, since tensor names and shard map are unchanged.
         It carries lm_head.weight / lm_head.weight_scale, so DSV41_LMHEAD_MXFP8 engages.
       - requant-viterbi-manifest.json: the manifest (not read by vLLM)
  d. Checks that the index weight_map equals the union of all 48 shard headers, and that each unit shard's inode
     is the verified output.
  config.json is still quant_method exl3 at 2.0 bpw MCG: same format, so no new config is needed.

10. Serving the new pack (not before the ARMS gate)
---------------------------------------------------
  SNAPSHOT_SHA=2.0bpw-mcg-viterbi-lmhead-mxfp8 ./run.sh
  run.sh resolve_snapshot: refs/<rev> is absent, so it uses snapshots/<rev>/ under HF_CACHE. SNAPSHOT_SHA is in
  run.sh's worker_config list, so spark2 resolves the same revision in its own cache. This is why the assembled
  snapshot has to exist on both nodes. Leave the serve pin (recipe.yaml revision 2.0bpw-mcg-lmhead-mxfp8) unchanged
  until it passes:
    - smoke_chat 323 and smoke_vision
    - correctness --full
    - ARMS.md step 6 ABAB against 2.0bpw-mcg-lmhead-mxfp8: ms/step at matched acceptance, noise-aware gate,
      quality quick and full
  The decode kernel is unchanged, so any speed change comes through DSpark acceptance only. That is unproven.
  Also check that p2b/coop engage as before (strict audit) and that lm_head MXFP8 does not self-disarm.
