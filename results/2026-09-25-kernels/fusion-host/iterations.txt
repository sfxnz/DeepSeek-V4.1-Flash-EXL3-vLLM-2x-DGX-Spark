fusion-host (k3 round 3): glue kernels, small bf16 GEMMs, host idle. Iteration log.
==================================================================================
Branch k3/fusion-host (from perf/kernels-r3). Every number below names its machine,
run and file. Timed runs: spark2 (clean GPU; pmon shows only Xorg/gnome-shell type G)
under .worktrees-spark2/.gpu.lock, SM clock 2190 MHz before/after each run.

0. Re-reading the r3 profile (profile/c1/c1-rank0.pkl, the c=1 L.A.I.L window)
-----------------------------------------------------------------------------
- The host is NOT the bottleneck of the eager chain: cudaLaunch/cudaGraphLaunch
  timestamps vs kernel start show the main thread launches every eager kernel of the
  next step 40-49 ms before the GPU runs it (kernel_study/fusion_host notes; step 120:
  draft graph launched at -48.7 ms, run at -6.3 ms). The "258 launches at ~4 us host
  cadence" are GPU-side back-to-back small-kernel costs (queued work), not host latency.
- The only host-bound GPU idle per step is the Engram stage: the main thread blocks in
  EngramDiskStager.stage -> hashes_ready.synchronize() until the GPU drains everything
  queued (the whole previous step), then runs the gather while the GPU has nothing
  queued. Step 120: DtoH ends at 0, sync returns +55 us, 2 pool futures start +190/+290
  us, finish +1.8/+2.4 ms, main wakes +2.57 ms, H2D +2.65 ms, graph starts +2.81 ms.
- 260 gaps > 1 ms in 250 steps: 251 are DtoH(hash) -> HtoD(rows), median 3.06 ms
  (p10 2.21, p90 3.94) profiled. Unprofiled estimate from the [gv2-census] read time
  before vs inside the profile window: 0.83 vs 1.39 ms/call median -> the profiler
  inflates this host span ~1.7x; unprofiled gap ~1.5-2.0 ms.

1. ITERATION 1: native Engram stage gather (KEEP, env DSV41_ENGRAM_NATIVE_STAGE=1)
-------------------------------------------------------------------------------
What: docker/patch/engram_native.c + engram_native_stage.py. After the stock hash +
sync, one ctypes call per table (GIL released): owned ids -> preadv2(RWF_NOWAIT) of
the 256 B fp8 row + 8 B ue8m0 row (misses: WILLNEED all, then blocking pread) ->
fp8 LUT x 2^(e-127) -> bf16 RNE straight into the pinned rows_host. Prefill (> 64
tokens) and every error take the stock stage. First 8 calls verified bit-exact
against the stock per-table gather; mismatch/error -> one DISABLED line, stock.

Numerics (engram_native_check.json, image canonical-e13, CPU): all 65536
(fp8 byte, ue8m0 byte) pairs bit-exact vs the stock torch chain (first cut had 512
NaN mismatches: torch's CPU bf16 conversion keeps NaN sign/payload -> 0x7FF0/0xFFF0,
not c10's scalar 0x7FC0; fixed), synthetic-table gathers both row orders and mixed
scales, ownership/padding 21/21, real tables 108/108 calls (2 layers x 2 TP ranks x
n in 1..8,64 x hot/dead-id/dropped-cache) bit-exact.

CPU critical path, spark2, rank 0, 2 tables, 300 iters after 30 warmup, arms
alternating, fresh ids every call (engram_stage_cpu_bench_spark2.json), us median
(p10/p90):

  hot       4  1461.7 (1056.5/1895.3)  274.1 (202.9/292.8) 307.8
  hot       8  2213.5 (1842.0/3023.2)  492.6 (438.5/627.8) 564.3
  pf        4  1702.9 (1145.5/2226.0)  141.7 (136.8/174.2) 380.5

2. ITERATION 2: token -> request map dedup across KV-cache groups (KEEP, env
   DSV41_ATTN_T2R_DEDUP=1)
--------------------------------------------------------------------------
Trace (c1-rank0.pkl, eager ops per step): DeviceScanInit/DeviceScan/compute_cuda_kernel
(repeat_interleave) 21.08/step each, arange 21.41, indexSelectSmallIndex 21.01, plus the
sub/copy/DtoD around them: build_attn_metadata makes one CommonAttentionMetadata per
KV-cache group and every group's builder (SWA, compressor, sparse MLA) rebuilds
token_to_req_indices (8 kernels) into its own buffer. 21 builds/step, all on the
critical path (3 before the draft graph, 18 before the target graph), each small kernel
~4.1 us of back-to-back GPU time.
What: decode_levers wraps CommonAttentionMetadata.token_to_req_indices. When a group's
metadata carries the same query_start_loc (GPU) and query_start_loc_cpu tensor OBJECTS
(weakref identity; every build_attn_metadata call slices fresh ones) and the same token
counts as the previous build, it copies the previous result (the [:max(mapped, tokens)]
view, tail zeros included) into its own buffer: 1 kernel instead of 8. Buffers,
addresses and values are the stock ones (graph-safe by construction).
Microbench (t2r_dedup_bench_spark2.json, spark2, image's real CommonAttentionMetadata,
21 groups per prep, GPU work queued first, 300 iters, arms alternating, every buffer
checked against repeat_interleave each iteration: 0 mismatches). GPU ops per prep
168 -> 28. GPU time per prep, us median (p10/p90):
  c=1 m=4            stock 684.4 (670.2/701.0)  dedup 141.0 (137.4/146.9)  -543.4
  c=2 m=8            stock 785.5 (681.2/836.8)  dedup 167.1 (144.5/284.5)  -618.4
  c=2 padded + tail  stock 881.9 (772.4/928.9)  dedup 255.3 (154.7/291.4)  -626.6
  c=1 m=1            stock 669.9 (663.9/686.4)  dedup 138.8 (135.8/142.9)  -531.1
Projected in the serve: 2 preps per step (draft 3 groups, target 18) -> 2 computations +
19 copies instead of 21 computations: -133 kernels, ~-0.52 ms/step (c=1), on the
critical path. Bit-exact by construction.

3. ITERATION 3: early Engram hash (KEEP, env DSV41_ENGRAM_EARLY_HASH=1, needs the
   native stage)
------------------------------------------------------------------------------
Why: with the native gather, the stage still starts only after the LAST eager launch of
the step (the hash is queued behind the block tables, slot mappings and ~18 groups of
attention metadata), so the gather (~0.15-0.3 ms) runs while the GPU has nothing queued.
Every input of the hash is final when GPUModelRunner.prepare_inputs returns
(input_ids, positions, query_start_loc; the lookback window reads num_computed_tokens /
all_token_ids, written only by the previous step's post_update).
What: docker/patch/engram_early_hash.py wraps GPUModelRunner.prepare_attn to launch the
model state's lookback kernel + the stage's hash + DtoH + event first; stage() consumes
them only for the same InputBatch object and token count (marked by a
DeepseekV41ModelState.prepare_inputs wrapper, consumed once), waits for that DtoH and
gathers while the GPU runs the queued metadata chain. Prefill sizes never go early. The
first 8 steps also run the stock late hash and compare int32 for int32 (mismatch ->
DISABLED line, late hashes kept, stock order after).
First bench attempt was invalid: 1 matmul of busy work left the host launching the
120-op chain AFTER the GPU was already idle, so the chain ran at host cadence and hid
nothing (native_early 499.0 vs native 471.9 us). Fixed with a calibrated 4 ms GPU spin
(torch.cuda._sleep, 2194 cycles/us) so the host runs ahead as in the serve.
Result (engram_stage_gpu_bench_early_spark2.json, spark2, 300 iters, 3 arms rotating,
120 small kernels queued between the early point and stage(), 0 mismatches, native and
early engaged): GPU span chain + stage, us median (p10/p90):
  n=4: stock 1933.7 (1536.0/2374.6)  native 496.5 (483.3/522.3)  native+early 322.9 (313.8/334.2)
  n=8: stock 2559.9 (2216.6/2995.9)  native 631.1 (619.7/642.1)  native+early 347.1 (338.0/358.6)
The early arm is chain + H2D: the gather is fully hidden. Beyond iteration 1:
-173.6 us (n=4), -284.0 us (n=8). Together vs stock: -1.61 ms (n=4), -2.21 ms (n=8).
