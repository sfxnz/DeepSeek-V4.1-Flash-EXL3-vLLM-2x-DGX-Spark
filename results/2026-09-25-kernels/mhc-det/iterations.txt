0. How the stock decode mHC split-K reduces (source + measurement)
---------------------------------------------------------------------
- GEMM: DeepGEMM sm120_tf32_hc_prenorm_gemm_impl<24, K, BLOCK_M=128, BLOCK_N=32, BLOCK_K=64,
  kNumSplits=16, 4 stages, 256+128 thr> (stock_src/kernel.sm120_*.{cu,sass}). Grid 16 CTAs.
  Split s writes its own slice mixes[s][m][n] / sqrsum[s][m] with PLAIN STORES (no atomics).
  Within a split: TF32 mma.sync m16n8k8 chain over its 20 k-blocks x 8 k-steps, one accumulator
  per 8-column n-tile. A = bf16 x widened to fp32; B = fn converted fp32 -> tf32 with
  round-to-nearest-EVEN on load (probe_b_round.json: RNE 60/60 cases bitwise, truncation 0/60,
  round-away 0/60; the mma itself truncates a raw fp32 B operand, probe.json raw_eq_trunc 1.0).
  sqrsum per lane: acc = acc + fma(a_lo, a_lo, a_hi*a_hi) per k-step, then + shfl_xor 2, + xor 1.
- Reduction: TileLang mhc_pre_big_fuse_with_norm (stock_src/pre_norm_s16_*.cu) sums the 16
  partials SERIALLY in split order 0..15 with plain loads (rms, then each of the 24 mixes).
- So the stock path is a fixed-order two-pass split-K and is deterministic at any fixed split
  count. Measured (gemm_check.json determinism, 1000 runs each, bitwise vs run 0):
    stock DeepGEMM 16 splits  T=4: 0 differing elements   T=8: 0
    stock DeepGEMM 40 splits  T=4: 0                      T=8: 0
    stock full pre (GEMM + TileLang fused norm) 16 splits T=4/8: 0;  40 splits T=4/8: 0
  => the R34 rejection of DSV41_MHC_DECODE_SPLITS=40 was NOT caused by a nondeterministic
  reduction. 40 splits is deterministic but numerically different from 16 (split order: maxabs
  6e-6, s1) and was bundled with WOA prepack; the selfcons A/A metric measures serve-level
  run-to-run divergence (baseline B boots are nonzero too). A plausible mechanism for more A/A
  divergence with 40: split count 40 only for T <= 64 while prefill chunks of the same tokens
  keep 16, so numerics then depend on how a token is batched (prefix-cache tail vs full prefill).
- Design consequence: instead of a new split-K order, reproduce the stock 16-split numerics
  BITWISE and make them fast. No numerics change => no quality A/B risk.
