coop-moe round 3: routed-MoE (p2b) decode kernel iterations
============================================================
Machine: spark2 GB10 (48 SMs, L2 24 MiB, SM 2184-2190 MHz during every run), image
dsv41-flash-exl3-sm121:canonical-e13, kernels JIT-built from the committed pin + patch chain
(kernel_study/p2b_coop/make_bench_r3.py; the same patch files the serve image applies).
Harness: kernel_study/p2b_coop/bench_r3.py. Real layer-20 weights (TP rank 0: 384 experts,
hidden 5120, local inter 1152, K=2 MCG) from the pack snapshot, census routing of the same layer
(s10 captures; m <= 4 consecutive tokens, m > 4 two independent 4-token windows), activations =
RMS-normalized Gaussian x the layer's real ffn_norm weight. Cold = 128 MiB read-flush before every
timed call + fresh routing per iteration; 200 timed iterations after 20 warmup, all arms
alternating in rotating order on identical routings; CUDA events per call. Every GPU run was
preceded by nvidia-smi pmon (only Xorg/gnome-shell with SM "-") and ran under spark2's GPU lock;
clocks sampled every 250 ms (runs/<tag>.clocks.csv). Raw JSON per run in this directory.

Variant ids = DSV41_P2B_COOP values. Numbers: median cold us per call (census routing unless
noted), p10/p90 in the JSON. "floor" = unique expert bytes / 250 GB/s (task definition);
"ceiling" = unique bytes / 232 GB/s, the measured spark2 read ceiling (it 9 below).

it 0  baseline (v0-base-r3.json)
  v0 p2b (served SORT=0) m=4 520.8, m=8 1014.8, m=1 181.2
  v1 round-2 coop (SORT=2) m=4 378.9 (-27%), m=8 670.3 (-34%); dup0 m=4 536.7 (+2.0%)
  Phase stamps (%globaltimer around every grid.sync): v1 m=4 = prologue 5.7 + gate/up 209.6 (20.3 of
  it waiting for the slowest block) + 3 elementwise phases 5.0 + down 108.1 (12.0 waiting) + output
  2.5 + 1.6, 7 barriers x 0.7. The phase tails (32 us) and the elementwise/barrier phases (20 us)
  are the overhead; within a phase the stream runs near the ceiling.
  ncu (v01-m4, /home/sfxnz/projects/data/dsv41-coop-moe/ncu): p2b issue slots 47%, long-scoreboard +
  barrier stalls 57% of samples; grid.sync spinning threads execute CCTL.IVALL (L1 invalidate) in a
  loop; A-operand loads (had_gate etc.) stall the HMMA (long scoreboard on the A registers).
  -> KEEP v1 as the reference, go after the tails and phases.

it 1  dataflow task list (widen_p2b_dataflow.py) v2 (4 blocks/SM) / v3 (3 blocks/SM)
  One grid.sync after the input Hadamard, then one atomic task counter over gate/up tiles
  (unit, 128-block, half, gate|up) followed by down tiles (unit, group); the 4th finished gate/up
  tile of (unit, 128-block) runs that block's epilogue (output Hadamard gate/up + SwiGLU + down
  input Hadamard, p2b's math op for op); down tiles wait on the unit's readiness count (acquire);
  one more grid.sync, fused down output Hadamard + fixed-order slot sum. Bit-identical to v1.
  v2 m=4 348.2, m=8 628.7: the task loop state pushed the MMA loop into spills (12 LDL/iter).
  v3 (__launch_bounds__(256,3), 80 regs, no spills) m=4 329.8, m=8 600.1, m=1 149.5 (p2b 182.3),
  dup0 m=4 483.4 (p2b 526.3: -8% with nothing to share). -> KEEP v3 (drop v2: spills).

it 3  per-warp tile accounting (v3-acct.json; stamped build, lane 0 of every warp)
  v3 m=4 per warp: span 326 us = pipeline fill 15.0 + MMA loop 262.1 + cross-warp reduction
  (incl. waiting for the block's slowest warp) 23.5 + between tiles (fence, counters, epilogue,
  task fetch) 25.9; 12.9 tiles/warp. 20% of every warp's time is per-tile overhead.

it 4  warp-stream kernel v8/v9 (p2b_ws_kernel): no block barrier per tile
  Each warp walks the block's task sequence on its own K-range, hands its partial to one of 2
  shared buffers, the last warp in reduces (same j order, same bits) and does the follow-up work.
  v8 (3 blocks/SM, 4-row chunks) m=4 337.9 = v3; accounting: reduction wait 23.5 -> 7.1 us/warp
  but the MMA loop grew 262 -> 285 us/warp: removing the waits only moved time into the loop.
  v9 (2 blocks/SM, PF 4, 8 rows) 362.4. DROP both: the loop is memory-bound, not barrier-bound.

it 5  memory ceiling probes (v4-stream.json, v4-bw.json, v4-ld.json, v4-gemm.json)
  - The same experts' trellis read with the coop tile pattern and NO decode (bench-only kernel):
    m=4 323.6 us = 214.7 GB/s, m=8 576.5 = 230.3 GB/s; a contiguous read of the same bytes is not
    faster (209.7 / 227.7). v6 on the same routings: 333.8 / 606.2 -> the full MoE kernel is
    within 3-5% of a pure read of its weights.
  - Plain contiguous read of 512 MiB: 227-232 GB/s median (max 235) for every blocks/SM (2-8),
    prefetch depth (1-8), load width (4/16 B/lane), L2 prefetch, and for ld.global.cs, ld.global,
    ld.global.nc, ld.L1::no_allocate, cp.async.cg 16 B and TMA cp.async.bulk 2 KB.
  - cuBLAS bf16 GEMV-class GEMM (N 64640 / 16384 x K 5120, m 4/8): 226-230 GB/s.
  => spark2's practical DRAM read ceiling is ~232 GB/s (85% of 273), not 250. The 249-250 GB/s
     quoted for the serve's lm_head/Markov GEMMs (spark1 trace3) is not reproducible here.
     Reported: % of the 250 GB/s floor (task definition) AND % of the 232 GB/s ceiling.

it 6  prologue prefetch / dataflow output (v5-pro-dfout.json, v5b-dfout-fix.json)
  v10 = v6 + each block's first task static and its first 6 k-slices of all K-ranges prefetched
  into L2 before the input Hadamard: m=4 331.8 (-0.6% vs v6), m=8 600.7, m=1 159.8 (v6 168.9).
  v11 = v6 + output (row, 128-block) written by the last of its 12 down tiles (per-tile fence +
  barrier + counter), no final grid.sync: 343.0 / 621.1 (+3%): the per-down-tile sync costs more
  than the output phase it removes.
  v12 = v10 + v11: FAILED the gates (one-hot bit-exact false at m=8, graph replay != eager at m=4/6).
  Root cause: after the counter barrier, warps re-read the task index from shared memory while
  thread 0 could already have overwritten it with the next task (no barrier in between). v11 had
  the same race and passed by luck. Fixed (index read before the barrier); v11/v12 re-checked
  (12 routings x m 1..8 x 3 sources, 32 replays): pass. Kept as a lesson: the gates caught it.
  -> KEEP v10.

it 8  cheaper tile publication (v7-cheap.json)
  v15 = v10 + CHEAP: a gate/up tile is published by thread 0's atom.acq_rel.gpu after the tile's
  closing __syncthreads (release is cumulative over the barrier; the CUTLASS GenericBarrier
  pattern) instead of __threadfence in all 256 threads + an extra barrier; epilogue readiness via
  red.release.gpu. m=4 313.6 vs v10 317.3 (-1.2%), m=8 = v10, m=6 -0.4%. KEEP.
  v16 = v15 + output (row, 128-block) by the last of its 12 down tiles, with the same cheap
  acq_rel counting (no fence, no extra barrier): m=4 +0.9%, m=8 +2% vs v10; its inlined output
  code spills 184 B and every down tile pays the RMW. DROP the dataflow output for good.
